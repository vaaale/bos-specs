# Feature Specification: Generic Service Secrets & Bastion Credential Routing

**Feature Branch**: `034-secrets-authentication`

**Created**: 2026-08-01

**Status**: Draft

**Input**: User description: "Generalize the WebDAV mount-token mechanism (033-vfs-mount) into a
generic BOS-wide client/secret system that any protocol/service can use. It must work identically
standalone and behind the multi-user Bastion reverse proxy, including when Bastion is configured
with Keycloak — without giving Bastion a Keycloak admin-API service account, without a native OAuth
mount client, and without Bastion hardcoding per-protocol path knowledge."

## Background

033-vfs-mount shipped a WebDAV mount-token system (`src/lib/webdav/tokens.ts`) scoped entirely to
the WebDAV endpoint. Bastion (`bastion/src/proxy.ts`) special-cased the single path
`/api/vfs/webdav` (`WEBDAV_PREFIX`/`isWebdavPath`): a request with no session cookie but a valid
`Authorization: Basic` header would resolve its username via `provider.getUser()`, forward the
password as a rewritten `Bearer` token, and route to that user's container.

Two problems surfaced:

1. Deployed Bastion images that predate that fix unconditionally redirect any cookie-less request
   to `/login` — including WebDAV clients, which cannot follow an HTML redirect, and which report
   this as a bare 302 on mount.
2. `KeycloakProvider.getUser()` is a stub that always returns `null` (Bastion has no local user
   registry when Keycloak owns identity), so even with the fix, WebDAV mounting behind
   Bastion+Keycloak cannot resolve a username and always fails.

Fixing problem 2 by giving Bastion a Keycloak admin-API service account was considered and
rejected: it adds a new privileged credential and doesn't fit this system's "no extra services,
state lives in files" model. A native, OAuth-capable mount client (mirroring how
`google-drive-ocamlfuse`/`rclone` do their own OAuth handshake) was also considered and rejected —
it requires shipping and maintaining a bespoke binary instead of using stock `davfs2`/Finder.

This feature replaces per-protocol, path-specific Bastion knowledge with a generic mechanism: any
BOS service can mint a secret; Bastion routes purely by looking up that secret's hash in a small,
non-reversible, per-user companion index it already has filesystem access to — never by asking an
identity provider "who is this," and never by hardcoding a path.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Mount WebDAV behind Bastion+Keycloak (Priority: P1)

An operator runs BOS behind Bastion configured with `AUTH_PROVIDER=keycloak`. They log into BOS
normally (full Keycloak SSO), go to Settings → Local Mount, and generate a mount token. They then
run `sudo mount -t davfs <url> /mnt/browseros` with that token as the Basic-auth password. The
mount succeeds and the drive is usable.

**Why this priority**: This is the reported bug and the specific case that was previously
impossible to fix without a Keycloak admin-API dependency we've ruled out. It's the reason this
feature exists.

**Independent Test**: Stand up Bastion with `AUTH_PROVIDER=keycloak`, generate a token via the
Settings UI, mount with `davfs2` using that token, and confirm file listing/read/write works — with
no Keycloak admin client credentials configured anywhere in Bastion.

**Acceptance Scenarios**:

1. **Given** a mount token generated by a logged-in Keycloak-authenticated user, **When** a WebDAV
   client presents it via `Authorization: Basic <anything>:<token>`, **Then** Bastion routes the
   request to that user's container and the mount succeeds.
2. **Given** no mount token has ever been generated for a given raw string, **When** a WebDAV client
   presents it, **Then** Bastion responds `401` with `WWW-Authenticate: Basic`, not a redirect.
3. **Given** Bastion's `KeycloakProvider.getUser()` remains a stub returning `null` and no Keycloak
   admin client is configured, **When** a valid mount token is presented, **Then** routing still
   succeeds (it never calls `getUser()`).

---

### User Story 2 - Mount WebDAV behind Bastion+simple auth (Priority: P2)

An operator runs BOS behind Bastion with `AUTH_PROVIDER=simple` (the previously-working case).
After this feature ships, mounting must keep working exactly as before — this story exists purely
to guarantee no regression while the routing mechanism is rebuilt underneath it.

**Why this priority**: Currently-working behavior must not regress; ranked below User Story 1 only
because it was already functional, not because it matters less.

**Independent Test**: Repeat User Story 1's test with `AUTH_PROVIDER=simple`; behavior must be
identical from the WebDAV client's perspective.

**Acceptance Scenarios**:

1. **Given** `AUTH_PROVIDER=simple` and a mount token generated via Settings, **When** a WebDAV
   client mounts with it, **Then** the mount succeeds exactly as it did under 033-vfs-mount.
2. **Given** a token is revoked via Settings, **When** a WebDAV client subsequently presents it,
   **Then** the request is rejected (401 from the container's own verification, same as today).

---

### User Story 3 - A new protocol adopts headless auth with zero Bastion changes (Priority: P3)

A BOS developer adds a second protocol/service (e.g. a future CalDAV or git-over-HTTP endpoint)
that needs to accept headless clients speaking HTTP Basic auth. They call the generic secret API
to mint and verify their own service's secrets. They make **no changes** to `bastion/src/proxy.ts`.

**Why this priority**: This is the generalization payoff — it's what justifies building a shared
mechanism instead of a second WebDAV-shaped one-off. Lower priority than the two mount-fixing
stories because no second protocol exists yet to prove it against.

**Independent Test**: Add a throwaway test service that mints a secret via the generic API under a
new namespace, present it via Basic auth to a path Bastion has never seen before, and confirm
Bastion routes it correctly without any code change to `proxy.ts`.

**Acceptance Scenarios**:

1. **Given** a new service namespace with a minted secret, **When** a Basic-auth request for that
   service's path arrives with no session cookie, **Then** Bastion resolves and routes it using the
   same generic lookup — the branch condition is "Basic auth present," never a path allowlist.
2. **Given** two different services each have a secret whose raw values happen to differ, **When**
   both are presented to Bastion, **Then** each resolves to its own service/user pairing without
   collision.

---

### User Story 4 - Standalone/local-dev behavior is unaffected (Priority: P1)

An operator (or developer) runs BOS directly, with no Bastion in front of it (`run-dev-supervisor.sh`,
or a single standalone Docker container). WebDAV authentication continues to be checked directly
against BOS's own encrypted secret store, with no dependency on Bastion or any companion index.

**Why this priority**: This is the majority deployment mode for local development and must not
regress; tied for P1 with User Story 1 because breaking it would be a foundational regression, not
a missing nice-to-have.

**Independent Test**: Run BOS standalone, generate a token, mount WebDAV directly against
`http://localhost:3000/api/vfs/webdav` with no Bastion process running at all.

**Acceptance Scenarios**:

1. **Given** no Bastion process is involved, **When** a valid token is presented as a Bearer token,
   **Then** BOS's own verification (against its own encrypted store) accepts it, unchanged from
   033-vfs-mount.

### Edge Cases

- A user's container has never been provisioned (no `data/` directory exists yet on disk) — the
  routing scan simply finds nothing there; this is not an error, just a non-match for that user.
- A user's `credentials-index.json` is missing, empty, or corrupted — that user is skipped during
  the scan; it must not abort or corrupt the scan for other users.
- A secret is revoked concurrently with an in-flight request using it — acceptable eventual
  consistency; the container's own (authoritative) verification is the final word regardless of
  what Bastion's routing index says.
- Revoking a secret must remove both the encrypted record and its companion index entry — a stale
  index entry left behind after revocation is not a security issue (the container's own check still
  rejects it) but is a hygiene bug this feature must avoid.
- The number of provisioned users grows over time — the routing scan is bounded by
  `MAX_CONCURRENT_INSTANCES` (default 50), not by request volume; this must stay small enough that a
  linear scan per request remains acceptably fast (see Success Criteria).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: BOS MUST provide a generic secret-issuing mechanism, namespaced by an arbitrary
  `service` identifier, usable by any BOS server-side feature (not specific to WebDAV).
- **FR-002**: Secret material MUST continue to be stored exactly as securely as 033-vfs-mount
  established: a per-secret salted, slow (scrypt) hash, inside the existing per-user encrypted
  `SecretsStore` (AES-256-GCM at rest). This feature MUST NOT weaken that guarantee.
- **FR-003**: Alongside the encrypted record, minting a secret MUST also write a minimal,
  non-reversible companion record (a fast, unsalted hash of the raw secret, plus which `service` it
  belongs to) to a plaintext file inside that same user's `data/` directory, so it can be read by a
  process that does not hold the encryption key.
- **FR-004**: Standalone BOS (no Bastion) MUST verify a presented secret directly against its own
  encrypted store, unchanged from 033-vfs-mount's behavior, and MUST NOT depend on the companion
  index to do so.
- **FR-005**: When running behind Bastion, a request with no session cookie but a parseable
  `Authorization: Basic` header MUST be routed by hashing the presented password and looking it up
  across every provisioned user's companion index — never by resolving the Basic-auth username
  against an identity provider.
- **FR-006**: This routing lookup MUST behave identically regardless of Bastion's configured
  `AUTH_PROVIDER` (`simple` or `keycloak`). It MUST NOT require Keycloak admin-API credentials or
  any other new privileged credential.
- **FR-007**: Bastion's role in this flow is routing only — it MUST forward the presented secret to
  the resolved container (rewritten as a `Bearer` token, matching 033-vfs-mount's existing
  contract) and MUST NOT itself decide whether the secret is valid. The target container's own
  verification (FR-002's store) remains the sole source of truth for authentication.
  the target container's own verification (FR-002's store) remains the sole source of truth for authentication.
- **FR-008**: The Bastion-side branch that triggers this routing MUST be based on the *shape* of
  the request (session-cookie absent, Basic auth present), not on an allowlist of paths. Adding a
  new protocol/service that uses this mechanism MUST require zero changes to Bastion's routing code.
- **FR-009**: Revoking a secret MUST remove both its encrypted record and its companion index
  entry.
- **FR-010**: 033-vfs-mount's existing WebDAV token endpoints (`src/app/api/vfs/webdav-tokens`) and
  the Settings → Local Mount UI MUST continue to work unchanged from the user's perspective; they
  become one caller of the generic mechanism (namespace `vfs-webdav`) rather than a bespoke
  implementation.
- **FR-011**: The companion index MUST NOT reveal the raw secret, and MUST NOT be usable on its own
  to authenticate a request (it is a routing aid, not a credential store).

### Key Entities

- **ServiceSecret**: A generic, per-user, per-service credential. Attributes: `tokenId`, `service`
  (namespace, e.g. `"vfs-webdav"`), `hash` (salted scrypt hash of the raw secret), `label`,
  `createdAt`. Stored in the existing per-user encrypted `SecretsStore`. Generalizes
  033-vfs-mount's `TokenRecord`.
- **CredentialsIndexEntry**: A per-user, per-secret routing record. Attributes: `hash` (fast,
  unsalted hash of the raw secret — a different, faster hash than `ServiceSecret.hash`, used only
  for lookup), `service`, `createdAt`. Stored in a single plaintext file per user
  (`data/system/credentials-index.json`), readable by Bastion via the existing per-user data
  bind-mount, never written to or read by any other user's container.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A WebDAV mount token generated behind Bastion+Keycloak, with no Keycloak admin client
  configured anywhere in Bastion, successfully mounts via `davfs2`.
- **SC-002**: A WebDAV mount token generated behind Bastion+simple-auth continues to mount
  successfully, with behavior indistinguishable from 033-vfs-mount to the WebDAV client.
- **SC-003**: Adding a second protocol/service that uses the generic mechanism requires zero lines
  changed in `bastion/src/proxy.ts` beyond what this feature itself introduces.
- **SC-004**: `bastion/src/proxy.ts` no longer contains any WebDAV-specific constant or path check
  (`WEBDAV_PREFIX`, `isWebdavPath` are removed, not just unused).
- **SC-005**: Revoking a secret via Settings makes it stop working for both authentication (already
  true today) and Bastion-side routing (new) within one request — no stale successful mounts after
  revocation.
- **SC-006**: The per-request routing lookup on Bastion completes without perceptible added latency
  at the default `MAX_CONCURRENT_INSTANCES` (50) scale.

## Assumptions

- Bastion continues to have the same filesystem access it has today (the `/user-data` bind-mount
  covering every provisioned user's `data/` directory) — no new mount or shared volume is
  introduced.
- The raw secret values this mechanism issues remain high-entropy, random, BOS-generated tokens
  (never user-chosen, low-entropy passwords) — this is what makes a fast, unsalted lookup hash
  acceptable for the companion index without reintroducing brute-force risk.
- OAuth device-code minting (for headless minting without an existing browser session) and a
  native OAuth-capable mount client are explicitly **out of scope** for this feature. They were
  discussed and rejected/deferred as separate, optional future work — this feature's job is only to
  make the existing Settings-UI-minted token routable everywhere, generically.
- Giving Bastion a Keycloak admin-API service account to implement `getUser()` is explicitly
  **out of scope** — this feature exists specifically to avoid that dependency.
- Per-user data isolation (one container never sees another user's data) is a hard constraint this
  feature must preserve; only the non-reversible companion index is cross-user-readable, and only by
  Bastion.
